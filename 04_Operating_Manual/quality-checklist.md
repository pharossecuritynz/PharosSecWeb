# Quality Checklist

Run through this before **any** client-facing deliverable is sent — draft or final, no exceptions.

## Content accuracy

- [ ] All findings are factually accurate and traceable back to source (notes, screenshots, discovery answers)
- [ ] Every finding has a stable finding ID, and cites a specific evidence type per [evidence-standard.md](evidence-standard.md) — not a vague "reviewer noted"
- [ ] Every high-priority recommendation has a corresponding finding; no recommendation appears without one behind it
- [ ] Every 90-day plan action traces back to a finding ID or an explicitly agreed improvement
- [ ] Risk rating and priority are both present and make sense together (see [risk-and-priority-methodology.md](risk-and-priority-methodology.md)) — not silently defaulted or copy-pasted from a similar finding
- [ ] No finding is overstated to justify further work
- [ ] Pricing/scope in any accompanying email matches what was actually agreed
- [ ] Client name, business name, and any specific details are correct throughout (check for leftover placeholder text or another client's name from a copied template)

## Plain-English standard

- [ ] Executive summary is understandable to someone with zero security background
- [ ] Every acronym is defined on first use
- [ ] No sentence requires re-reading to understand
- [ ] Tone matches [../01_Brand/tone-of-voice.md](../01_Brand/tone-of-voice.md) — calm, plain, no fear language

## Structure and formatting

- [ ] Follows [reporting-standards.md](reporting-standards.md) structure (summary first, detail after)
- [ ] Consistent priority labelling (Now / Next / Later / Monitor)
- [ ] Headings, fonts, and colours match [../01_Brand/visual-identity.md](../01_Brand/visual-identity.md)
- [ ] No broken formatting, inconsistent numbering, or leftover template comments/brackets

## Scope and boundaries

- [ ] Deliverable matches what was scoped in the proposal — no silent scope creep or scope reduction
- [ ] Limitations/boundaries note is included where relevant (see [../03_Services/service-boundaries.md](../03_Services/service-boundaries.md))
- [ ] Confidentiality footer is present (see [reporting-standards.md](reporting-standards.md))
- [ ] No unsupported legal or compliance claim ("compliant," "certified") appears anywhere, including in privacy content — see [nz-guidance-mapping.md](nz-guidance-mapping.md)
- [ ] No accidental internal notes, draft brackets, credentials, API tokens, or personal information not meant for the client survive into the final document
- [ ] NZ guidance references (NCSC, Privacy Act, IPP numbers) are current — see [nz-guidance-mapping.md](nz-guidance-mapping.md) for the last-verified date

## Final checks

- [ ] Spelling and grammar checked (read aloud or use a tool — don't rely on skimming)
- [ ] File named correctly per the naming convention in [reporting-standards.md](reporting-standards.md)
- [ ] Correct file format (PDF for final delivery, unless client specifically needs editable format)
- [ ] Attachments actually attached before hitting send

## Before sending the accompanying email

- [ ] Recipient(s) correct — double check "reply all" risk if multiple client contacts are cc'd
- [ ] Tone of the email itself matches brand voice
- [ ] Clear next step stated (call scheduled? action needed from client? nothing further needed?)

## A useful gut check

Before sending, ask: *"If the client's most technical IT person and their least technical owner both read this, would they both come away with an accurate, clear understanding?"* If either would be confused or misled, revise before sending.

## Sign-off

Record who reviewed this deliverable and when, even in a solo practice — this is what makes "no exceptions" auditable rather than just a stated intention.

**Reviewed by:** [Name] **Date:** [Date] **Result:** ☐ Ready to send ☐ Needs revision (see notes)

## Assumptions / needs founder input

- If associates or subcontractors are ever engaged, this checklist should be run by a second person (peer review), not just self-checked by the author. Until then, the sign-off above is still completed by the same person who drafted the deliverable — a deliberate pause, not a rubber stamp.
